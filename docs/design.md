# komimi の設計と由来 (2026-10-07)

## なぜ作ったか

端末 (ESP32-S3 / ESP32-P4) で日本語カナの聞き取りを完結させたい。先行の oido (lokutor-ai) は同じ土俵の
エンジンだが GPL-3.0 で、製品ファームに組むなら商用ライセンスが要る。「エンジンを作り直すをトライするべき」
という指示で、**GPL のコードに依存しない**実装を一から書いた。

## 何に基づいているか (由来)

- アーキテクチャ: NVIDIA NeMo `stt_en_conformer_ctc_small` の公開設定 (`model_config.yaml`、CC-BY-4.0):
  log-mel 80 (n_fft 512 / 25 ms / 10 ms、pre-emphasis 0.97、Slaney mel、log(x+2^-24)、特徴ごとの標準化)、
  striding ×4 (3×3 s2 ×2 → Linear)、×√d、16 層 d=176 h=4 ff=704 k=31、相対位置 (Transformer-XL 型、bias_u/v)、
  半分ずつの FF、conv module (pw → GLU → dw → SiLU → pw、BatchNorm は dw に畳み込み済み)、最終 LayerNorm、
  CTC head (blank = 最後の列)。これらは論文 (Gulati+ 2020) と NeMo (Apache-2.0) の公開仕様。
- 重み: 元は NeMo の CC-BY-4.0 の重みを、oido の学習スクリプトで日本語カナに微調整したもの (`out_v1/last.pt`)。
  **重みはプログラムの出力でソースではない** (GPL は重みに及ばない)。komimi の `export.py` (現在は非公開の学習側 komimi_train/export.py) はテンソル名を
  読み替えるだけで、以後の学習 (`train.py`、同じく komimi_train/) は komimi 自身のコードで行う (v3 以降は oido に依存しない)。
- 検証: oido の学習モデルを**黒箱**として同じ音を入れ、logits を比べた (argmax 一致 99%+、log-softmax 後の差は
  末尾 1 フレームの窓の扱いの差だけ)。oido のエンジン (C) のソースは読んでいない (ビルドして数字を取っただけ)。
- 著者 (Claude) は oido の `export_nemo.py` / `eval_engine.py` を前日に実行のため目にしている。コピーはして
  いないが、厳密な「2 人体制のクリーンルーム」ではない。製品に組む前に法務確認を推奨。

## 独自に決めたこと

- `.kmm` 形式: 64 byte 境界、行ごと対称 int8 + float の scale、float の小物、token 表 (komimi/kmm.py)
- 量子化: 重みは行ごと対称 int8、活性はベクトル (フレーム) ごとに動的 int8、int32 積和 → float。
  LN / softmax / SiLU / GLU / 深さ方向 conv / 残差は float。学習側の擬似量子化 (`QLinear.fake_quant`) と同じ分解
- ストリーミングの境界 (学習側 komimi_train/model.py 冒頭と csrc/km_stream.c 冒頭に同じ記述):
  注意は chunk 内の先も見る + 左 left フレーム、dw conv は chunk の先を 0 扱い、標準化は固定 mean/std、
  サブサンプリングは系列全体と同じ (chunk c の出力はメル行 [64c-3, 64c+64) だけで決まるので先読みはチャンク外に出ない)。
  マスク学習 (全系列) と逐次計算 (C) が **同じ値** になることを試験で確認 (max |Δ| 1e-4)
- 内積カーネル 1 関数 (`km_gemv_s8`) に機種依存を閉じ込める。generic C / AVX2 を実装。
  S3 (Xtensa PIE) と P4 (RISC-V + SIMD) は現状 generic C でビルドだけ通してある

| モデル | 層 | int8 .kmm | dev 300 stream CER (C) | 計算量 |

| v3 / v5 | 16 | 14.0 MB | 29.9% / 27.6% (chunk 32) | 19.2 M MAC/フレーム |

これに chunk 32 を足す (v7 = v6 から動的チャンク学習)。

### int8 の注意スコア (KM_ATT_INT8、端末ビルドの既定)

(q+bias_u)/(q+bias_v) と K・P をヘッドごとに 16 の倍数 (44 → 48) に零詰めした int8 にし、スコアを SIMD 内積で出す。
dev 300 stream: 30.08% (float スコア) → 30.15%。精度コストはほぼ無し。

### 4-bit 重み (8 MB flash の端末向け、v4 = int4 QAT)

| 重み | .kmm | dev 300 stream CER (C) |
|---|---|---|
| int8 (v3) | 14.0 MB | 29.87% |
| int4 を後から量子化 (PTQ、v3) | 7.5 MB | 41.96% (dev 100) |
| **int4 QAT (v4)** | **7.5 MB** | **31.24%** |

int4 は 1 byte に 2 値 (下位ニブル = 偶数列)、行ごとの scale。C では行を int8 に展開してから同じ内積カーネルに通す。
列が奇数の行列 (conv1 の 9 列) だけ int8 のまま。

## 端末 — M5StickS3 (ESP32-S3 240 MHz、8 MB flash dio、8 MB octal PSRAM) 実測 (2026-10-07)

int4 QAT モデル (7.5 MB) を `model` 区画から mmap、chunk16/left128、KM_KV_INT8、4 秒の合成音 (6 チャンク)。
書き込みは手元 PC で `esptool write_flash 0x0 <merged.bin>` (rfc2217 経由はこの端末の USB-Serial/JTAG がリセットで
再列挙されるため使えなかった)。

| 版 | 1 チャンク (640 ms) | RTF | 備考 |
|---|---|---|---|
| 汎用 C、フレームごとに重み読み | 31.0 s | 46.5 | 実効 10 MMAC/s |
| + PIE int8 内積 (`km_dot_s8`、自己診断 PASS、815 MMAC/s) | 18.2 s | 28.0 | 内積は速いが重み読み・展開がフレームごと |
| + チャンクまとめ処理 (重み 1 回/チャンク、注意は鍵 1 行で全問い)、int4 展開を表引き | 3.96 s | 5.9 | mel 421 / sub 1109 / ff 1196 / att 161+531 / conv 521 ms |
| + 疎メル (RAM)、重み 6 MB を PSRAM に | 3.41 s | 5.1 | mel 48 ms。重みの置き場はほぼ効かず (読み出し帯域は律速でない) |
| + 速い expf、conv1 を PIE 経路、gather を連続読み、xq を内部 RAM | **2.82 s** | **4.2** | sub 820 / ff 861 / att 145+476 / conv 445 / head 20 ms |

マイクロベンチ (同端末): `dot n=704` 815 MMAC/s、`dot n=176` 570 MMAC/s (309 ns/回 = 固定費 ~40 cycle)、
`gemv int4 704×176 ×16 本` 295 MMAC/s (内部 RAM) / 269 (PSRAM)、`gemv int8 352×176 ×16` 431 MMAC/s、
int4 展開 33.5 ns/byte、conv1 (176×9 スカラ) ×1360 = 95 ms。

結論: S3 ではこの 13M モデルは **RTF 4 前後**。短い内積の固定費が支配的で、次の一手は「16 行を QACC に
列ごとに積む重み固定型カーネル」(推定 2 倍) と注意スコアの int8 化だが、それでも実時間には届かない。
S3 で実時間にするなら 8 層・d=144 級の小型モデルか chunk 32 (遅延 1.3 s)。本命は P4。

### デモファーム (esp32/demo_s3、2026-10-08)

M5StickS3 で マイク (ES8311、16 kHz) → komimi (v8、chunk 16、無音ゲート −58 dBFS) → LCD (ST7789 240×135) にカタカナを流す。
ES8311/PM1/LCD の初期化は Aunvox クライアント (同作者、Apache-2.0) から流用、カタカナは IPA ゴシック 15px から 16×16 ビットマップを生成
(`main/font_kana16.h`、97 字)。LCD の転送は 16 行の帯に分けて内部 DMA バッファを 4 KB に (komimi の作業領域に内部 RAM を回す)。
PSRAM の音声リング 20 秒 (喋っている間の遅れを無音で取り戻す)。ヘッダに入力レベル (しきい値の印つき)、RTF、溜まっている秒数。
ボタン A: 表示クリア、B: 無音ゲート on/off。段落: ゲートで 2 チャンク連続スキップ、または token が 1.5 秒出なかったら改行。

実機: 認識は動く。喋ってから表示まで 0.7〜1.3 s (chunk 640 ms + 計算 ~600 ms、640 ms ごとにまとめて出る)。
「最初の文字が二重になる」(例: タイトルが kkomimi) は 2 つの原因が重なっていた: (1) **LCD の帯転送で同じ DMA バッファを使い回し**、
送り終わる前に次の帯で上書きしていた (左端 = 最後の帯が二重、右端 = 最初の帯が化ける) → 6 本のリングに。(2) **マイクのクリップ**:
Aunvox 向けのゲイン (アナログ +24 dB + デジタル +8 dB) だと手元の声が −7 dBFS まで来てクリップし (クリップ計数で確認)、
子音の立ち上がりが潰れて認識側でも「タタイムズ」のような重複が出た → アナログ 12 dB・デジタル 0 dB に。
復号側の「接頭辞重複の除去」は効果が無く (dev −0.06pt、合成音の「ココナッツ」等は壊さないが実会話の重複も直せない) 既定 off。
**USB 給電中のキーキー音は PM1 の充電器 (`PWR_CFG` bit0 CHG_EN) のスイッチング**で、デモ中は充電を切ることで消えた
(外部 5V ブースト off だけでは残る。Aunvox クライアントにも同じ現象あり)。

## 端末 — ESP32P4-M3-DEV (ESP32-P4 rev1.0、360 MHz ×2 コア、16 MB flash dio、32 MB hex PSRAM) 実測 (2026-10-07)

**int8 フルモデル (14 MB、ストリーミング CER 29.9%)** を `model` 区画 (0x110000、14 MB) から PSRAM に写して実行。
P4 の SIMD (`esp.vmulas.s8.xacc`、S3 の PIE と同系で接頭辞と XACC の名前が違う) で自己診断 PASS、884 MMAC/s。

|---|---|---|---|
| 1 コア、PSRAM 20 MHz (IDF 5.3 の既定) | 1.80 s | 2.7 | mel 30 / sub 457 / ff 618 / qkv 116 / score 320 / conv 248 / head 14 |
| **2 コア** (gemv は行分割、注意は鍵/相対位置/ヘッド分割)、PSRAM 200 MHz | **0.97 s** | **1.46** | mel 30 / sub 208 / ff 337 / qkv 62 / score 166 / conv 165 / head 6 |

マイクロベンチ (P4 1 コア): dot n=176 753 MMAC/s (234 ns/回)、gemv int8 352×176 ×16 本 585〜677 MMAC/s、
gemv int4 704×176 ×16 本 361〜421 MMAC/s、int4 展開 27.9 ns/byte。

翌朝 (2026-10-08、PC 側エージェント `tools/pc_agent.py` 経由でサーバーから直接焼けるようにしてから) の追い込み。
v5 (動的チャンク) を chunk 32 で、段階内の細かい計測を入れて 1 つずつ潰した:

| 手当て | 1 チャンク (1.28 s) | RTF |
|---|---|---|
| v5 chunk 32、融合ロードカーネル (偶数ブロックのみ)、int8 注意スコア | 1792 ms | 1.34 |
| + 融合カーネルを奇数ブロックにも、計測 (gemv は 522 ms = 1/3 だけと判明) | 1720 ms | 1.29 |
| + SiLU/GLU を表引き、dw conv の `%` を除去、48 要素固定の内積 | 1561 ms | 1.17 |
| + 活性を inline (別 TU の関数呼び出しだった)、softmax の exp も表引き、conv1 を float、**値の足し込みを int8 SIMD (V 転置リング)** | 1356 ms | 1.02 |
| 実音声 6.1 s (dev の発話) で計測、h1 を内部 RAM | — | **0.99** |

端末の認識結果はホストと 1 文字差 (ソ**シ**スル / ソスル、float の丸め順の差で、正解はむしろ端末側)。
途中で踏んだ罠: `MALLOC_CAP_INTERNAL` が RTC (LP) RAM を返すことがあり、そこへの SIMD ベクタロードは Load access fault
→ `MALLOC_CAP_DMA` を足して通常 SRAM に限定。chunk 32 の作業バッファは内部 SRAM ぎりぎりなので S (スコア) と mel は PSRAM。

内訳 (1.28 s チャンクあたり、合計 1294 ms): gemv 521 (FF 151、conv2 ~150、q/k/v/o/pw ~130、head 10)、conv dw 73、

呼び出し側が音を溜めておけば喋っている間の遅れを無音で取り戻せる。

実時間 (RTF < 1) までの残りの手 (上の表の前に書いたもの。参考): (1) 注意スコアを int8 SIMD に (166 → ~40 ms)、(2) 16 行を QACC に列ごとに積む
重み固定型カーネル (短い内積の固定費 ~50 cycle/回を消す。gemv の実効 2 倍見込み)、(3) chunk 32 (遅延 1.3 s、
重みの読み/呼び出し回数が半分。動的チャンク学習が要る)、(4) 400 MHz (新しい IDF)。どれか 2 つで届く見込み。
S3 (RTF 4.2) との差は、クロック 1.5 倍 × 2 コア × 短い内積の固定費の差。

### ビルドの構成

`esp32/` は S3・P4 両方でビルドが通る (アプリ 240 KB)。重み 14 MB は `model` 区画からの mmap で直読み。
ストリーミングの作業メモリは chunk16/left128 で、float のまま 5.6 MB (KV キャッシュ 3.2 MB + 相対位置の射影 1.8 MB)、
`-DKM_KV_INT8` (端末ビルドの既定) で **1.9 MB** (KV と射影を行ごと int8。logits の差は最大 2 だが argmax は一致、CER は下の表)。
conv1 は 3 行のリングで逐次計算 (1 MB → 85 KB)。S3 (PSRAM 8 MB) / P4 (16-32 MB) どちらにも載る。

計算量は 1 出力フレーム (40 ms) あたり **19.2 M MAC** (層 12.7 M、サブサンプリング 6.3 M — うち conv2 が 5.6 M、head 0.2 M)、
実時間には 0.48 GMAC/s。実機は未計測 (このサーバーに基板が無い) で、推定は:
S3 240 MHz の generic C で RTF ≈ 2 (間に合わない)、PIE の int8 積和を実効 6 MAC/cycle 出せれば ≈ 0.33、
P4 400 MHz は generic C で ≈ 1.2、SIMD で ≈ 0.2。つまり **S3 では `km_dot_s8` の PIE 版が必須**、P4 でも SIMD 版が要る。
重みはフラッシュ直読みなので、実効値はフラッシュ帯域 (S3 の octal 80 MHz で ~40-80 MB/s、1 チャンクあたり 14 MB 読む
= 0.2-0.35 s/640 ms) にも縛られる。

### 出だしの取りこぼしと「発話前の音」の増強 (同日夜)

実機で「最初の 1 文字 (特に母音) が落ちる」との指摘。dev 300 の先頭に 1.2 s の雑音 (−60 dBFS) を足して無音ゲート on で測ると、
1 文字目の一致率が 56.7% → 45.0% に落ちる (無音 (0) を足しても 47%、雑音の位置を変えても同じ → チャンクの位相もゲートも無関係)。
外れ方は「アーエーイマミタイ → エーイマタイ」「エースパワー → パワハラ」「ウンソレカラ → ソレカラ」のような母音始まりの脱落と、出だしの子音の取り違え。
学習の切り出しが発話頭から始まるため、モデルが「音が続いた後の発話の出だし」を知らないのが原因。
エンジン側の対策 (声の直前のチャンクを流す / 立ち上がりに格子を合わせ直す) では一致率は変わらなかった。

学習側で、発話の前に 0.1〜1.0 s の無音か雑音 (−70〜−45 dBFS) を確率 0.5 で足す増強 (`--lead_pad`) を入れ、v12s を 20k step 追加学習 (lr 1e-4):

| v12s c16 | 発話頭から (pad 0) CER | 雑音 1.2 s の後 CER | 同 1 文字目一致 |
|---|---|---|---|
| 増強なし | 24.75% | 25.62% | 45.0% |
| **増強あり** | **24.38%** | **25.26%** | **51.7%** |

pad 0 も悪化しないので採用 (models/ と端末を更新)。以後の学習 (v12 の段階 2 以降) は既定でこの増強が入る。
データの内訳: ReazonSpeech all の split_0〜4 (約 5,400 h) + large (1,250 h) + 346 h、教師はすべて kana-whisper の読み。

## ストリーミングの位相と先行文脈 (2026-10-08、v10 c32 / dev 300、C エンジン)

「チャンクの出だしのタイミングで精度が変わるか」を、dev 音声の先頭に無音 (0 または −60 dBFS の白色雑音) を足してチャンク格子をずらして測った。
チャンク 32 = 1,280 ms なので、320/640/960 ms は格子の位相がずれ、1,280 ms は位相が元に戻る (先行文脈だけが増える)。

| 先頭に足した長さ | stream c32 (0 詰め) | stream c32 (雑音) | 全文脈 (0 詰め) | 全文脈 (雑音) |
|---|---|---|---|---|
| 0 ms (従来の測り方) | 23.24 | — | 22.20 | — |
| 320 ms (位相 1/4) | 24.11 | 24.14 | 22.54 | — |
| 640 ms (位相 1/2) | 24.42 | 24.64 | 22.88 | 22.81 |
| 960 ms (位相 3/4) | 24.70 | 24.77 | — | — |
| 1,280 ms (位相 0、文脈だけ増) | 24.48 | 24.31 | 22.82 | 23.12 |

- **大きいのは位相でなく「発話の前に音があるかどうか」**: 全文脈でも +0.6〜0.9 pt。学習データ (ReazonSpeech の切り出し) は発話が音声の先頭から始まるので、
  モデルが「ストリーム開始 = 発話開始」に慣れている。実機のマイク入力は常に先行文脈がある側なので、この dev の数字より 1 pt ほど悪い状態が実使用の基準になる。
- 位相そのものの効果は ±0.3 pt 程度 (320 ms が最良、960 ms = 発話の出だしが chunk 末尾に来て先読みが効かない位置が最悪)。
- ストリーミング特有の上乗せ (全文脈との差の拡大) が +0.3〜0.6 pt。
- 対策 (学習側、v11a 段階 2 / v12 から): チャンク格子の開始位置をバッチごとにランダムにずらす `--chunk_shift` (既定 on)。先頭の詰め物フレームは鍵としても conv の入力としても見えない扱いにして、格子だけをずらす。
  発話前の雑音・無音を足す増強も有効なはず (未実装)。
- 実機側の対策候補: 無音ゲートが再び開いたとき、音の立ち上がりにチャンクの頭を合わせ直す (格子を再アンカー)。

## kana-whisper をブラウザで (web/kw_worker.js、2026-10-08)

比較ページに教師モデル (sbintuitions/kana-whisper、large-v3-turbo 系 809M) を transformers.js 3.7 + ONNX Runtime Web (WebGPU) で載せた。
ONNX は optimum で書き出し、量子化の組み合わせは dev 20 発話 (正解 = 同じモデルの GPU 出力) を CPU で流して選んだ:

| 構成 | カナ CER | 大きさ |
|---|---|---|
| encoder fp32 + decoder fp32 | 1.12% | 2,548 + 688 MB |
| encoder **fp16** + decoder fp32 | 1.12% | 1,274 + 688 MB (**採用**) |
| encoder fp32 + decoder q4 (MatMulNBits、block 32) | 4.25% (accuracy_level 4 だと 5.82%) | 334 MB |
| encoder int8 (動的量子化) + decoder fp32 | 4.92% | 645 MB |
| encoder **q4f16** (MatMulNBits on fp16) + decoder fp32 | 3.13% | 370 + 688 MB |
| encoder q4f16 + decoder q4 (**軽量モード**) | 4.47% | 370 + 334 MB |
| encoder fp16 + decoder q4 | 3.36% | 1,274 + 334 MB |

- 4 層デコーダの turbo 系は 4-bit に弱く、エンコーダの int8 も効く。fp16 は無損失。ページでは**軽量** (q4f16 + q4、0.7 GB、教師比 +3 pt) を既定にし、**精度優先** (fp16 + fp32、2.0 GB) を選べる。
  2.0 GB 版は取得後の WebGPU 初期化 (シェーダのコンパイルと GPU メモリ確保) で止まって見えることがあり、GPU メモリ 3 GB 級が要る。取得の進み具合・GPU の素性 (f16 対応、バッファ上限)・初期化中の表示を出すようにした。
- 罠: torch 2.14 の torch.onnx.export は dynamo 既定で、optimum 1.24 と外部データのファイル名が食い違って落ちる → 旧エクスポータ (dynamo=False) を強制。
  accelerate が無いと merged decoder の重みが重複して 1.4 倍。onnx の外部データは同じ場所へ書き直すと追記で肥大する。
  merged decoder (If の部分グラフ) は fp16 変換器 (onnxconverter_common / ORT) が部分グラフの型を揃えられず読めない。quantize_dynamic は If の中を量子化しないので「q8」は大きさが変わらない。
  transformers.js の dtype と接尾辞: fp16 → `_fp16`、q4 → `_q4`、q8 → `_quantized`、fp32 → 接尾辞なし。Worker のスクリプトはブラウザに強く残るので URL に版を付け、nginx は `Cache-Control: no-cache`。
